# rag-bench

Two benchmarks on one Korean RAG corpus. **Part 1** (below): a retrieval-only benchmark of **FAISS, pgvector (ParadeDB), Milvus and OpenSearch** for a Korean RAG
application. It answers two separate questions:

1. **ANN engine**: at the same HNSW settings and recall, which store is faster and lighter?
   Ground truth is exact kNN, so this isolates the vector index from the embedding model.
2. **Retrieval pipeline**: what each store can do for search quality (dense, Korean BM25,
   hybrid with RRF, and reranking), scored against synthetic qrels.

Embedding and reranking models are served on a DGX Spark-class machine (Lenovo PGX, GB10) with vLLM.
The DBs run in Docker on a separate workstation with the same limits (4 CPU / 6 GB each), one at a time.

Full results: [results/REPORT.md](results/REPORT.md) (run 2026-10-20). How the work went, the decisions and the
lessons are in the [wiki](wiki/index.md).

**Part 2** ([PRD.md](PRD.md), [results](results/agentic/REPORT.md), run 2026-10-23) puts agents on top. It asks
whether a general agent runtime (Hermes Agent) with retrieval tools beats a RAG-specific workflow, and whether
decision models (Laya, Kev) can replace LLM tool calling for tool selection. See [Part 2](#part-2-agentic-rag).

## Findings (2026-10-20 run)

| | FAISS | pgvector | Milvus | OpenSearch |
| --- | --- | --- | --- | --- |
| p95 at recall@10 ≥ 0.95, 209k vectors | 0.64 ms | 4.21 ms | 2.72 ms | 2.70 ms |
| QPS at 1 / 8 / 32 clients, 209k vectors | 1784 / 5304 / 4755 | 232 / 760 / 610 | 352 / 777 / 589 | 460 / 1093 / 1143 |
| Build time, 209k vectors | 66 s | 214 s | 217 s | 492 s |
| Container memory after build, 209k vectors | (in-process) | 2.8 GiB | 3.4 GiB | 5.5 GiB (3 GiB JVM heap) |
| Filtered recall at 1 % / 10 %, 209k vectors | 0.53 / 0.86 | 1.00 / 0.90 | 1.00 / 0.99 | 0.54 / 0.86 |
| nDCG@10, hybrid + rerank, 209k vectors | 0.854 (dense + rerank) | 0.863 | 0.862 | 0.866 |
| p95 of dense top-100 / BM25 top-100, 209k vectors | 1.3 ms / – | 67 ms / 162 ms | 4.3 ms / 4.2 ms | 6.9 ms / 6.6 ms |

- **Search quality barely depends on the store.** Dense nDCG@10 is the same everywhere (0.79 base,
  0.73 full). Korean BM25 is close across nori and lindera (0.81–0.82 base), and adding it through
  hybrid RRF gains about 0.04. The reranker adds the most: about +0.09–0.11 nDCG@10.
- **The pipeline cost is dominated by the models, not the DB.** On the PGX, embedding one query
  takes ~16 ms and reranking 50 passages takes ~240 ms (p50), against 2–7 ms for the search itself.
- **Filtered search is where the stores really differ.** At 1 % selectivity, Milvus and pgvector
  (the planner picks the B-tree plus an exact sort) keep recall at 1.0. OpenSearch and FAISS
  run HNSW with the filter and fall to ~0.5.
- **pgvector slows down once the table outgrows shared_buffers.** At 209k rows, top-100 and BM25
  (pg_search) p95 reach 67 ms and 162 ms.

## Setup

| Part | Choice |
| --- | --- |
| Corpus | 1,000 Korean Wikipedia articles (2k–20k chars) → 9,069 chunks of ≤500 chars (`base`) |
| Scale test | `full` = base + 200,000 distractor chunks from other Korean Wikipedia articles |
| Queries | 598 questions generated by Qwen3.8-27B (one per sampled base chunk, paraphrased); the source chunk is the only relevant passage |
| Embedding | `BAAI/bge-m3` dense, 1024-d, L2-normalised, inner product |
| Reranker | `BAAI/bge-reranker-v2-m3`, top-50 candidates |
| Index | HNSW M=16, efConstruction=200 everywhere; `ef_search` swept 16→512 |
| Korean BM25 | OpenSearch nori · ParadeDB pg_search lindera(korean) · Milvus lindera ko-dic · FAISS none |
| Hybrid | client-side RRF (k=60) of dense top-100 and BM25 top-100, identical for every store |
| Metadata filter | random `tenant` 0–99 per chunk; filters `tenant < 1/10/50` = 1/10/50 % selectivity |

| Store | Version |
| --- | --- |
| FAISS | `faiss-cpu` `IndexHNSWFlat`, in-process, 4 OpenMP threads |
| pgvector | `paradedb/paradedb:latest` (PostgreSQL 18, pgvector 0.8.6, pg_search 0.26) |
| Milvus | `milvusdb/milvus:v2.6.25` standalone (etcd + MinIO) |
| OpenSearch | `opensearchproject/opensearch:3.9.0` + `analysis-nori`, faiss engine |

## Run

```bash
uv sync
export PGX_HOST=<model host>              # vLLM: LLM :8000 (synth only), bge-m3 :8001, reranker :8002
uv run python -m rag_bench.prep            # corpus: data/base.parquet, data/distractors.parquet
uv run python -m rag_bench.synth --n 600   # OpenAI-compatible LLM at $PGX_HOST:8000 (or LLM_URL)
scp scripts/serve-retrieval.sh pgx: && ssh pgx bash serve-retrieval.sh   # bge-m3 :8001, reranker :8002
uv run python -m rag_bench.embed_all       # data/emb_*.npy
scripts/run-all.sh                         # every store × {base, full}; STORES="milvus" to pick
uv run python -m rag_bench.report          # results/REPORT.md + results/ann_pareto.png
```

## Layout

```
rag_bench/prep.py          corpus + chunking + tenant metadata
rag_bench/synth.py         LLM query synthesis (qrels)
rag_bench/embed_all.py     one-off embedding of corpus and queries
rag_bench/stores/          one adapter per store, same interface (see stores/__init__.py)
rag_bench/bench.py         build, ANN sweep, QPS, filtered search, retrieval quality
rag_bench/model_latency.py per-query embed / rerank latency on the PGX
rag_bench/report.py        tables + chart
docker/                    one compose file per DB
```

## Fairness notes and gotchas

- **Same vectors everywhere.** Embeddings are computed once, so the DB comparison excludes embedding latency.
  Model latency is reported separately.
- **Compare at equal recall, not equal `ef`.** Each engine maps `ef` differently, so the report picks
  the smallest `ef` that reaches recall@10 ≥ 0.95.
- **pgvector on small tables:** the planner switched to an exact sort instead of the HNSW index at
  `ef_search` 32 and 64 (23 ms instead of 1–2 ms, recall 1.0). The adapter sets `enable_seqscan = off`.
  For filtered queries the planner may still use the `tenant` B-tree and an exact sort, which is legitimate
  and gives recall 1.0.
- **OpenSearch** is force-merged to one segment so that it searches a single HNSW graph, like the others.
  For filtered kNN it switches to exact search only when the filtered set is below
  `index.knn.advanced.filtered_exact_search_threshold`, which is unset here. That is why its recall
  at 1 % selectivity is ~0.54. Setting the threshold should fix it; this run did not test that.
- **Milvus segments:** with default settings, a growing segment seals at 12 % of 1 GB, so 209k vectors
  ended up as 10 segments of ~20k each. Compaction did not merge them. Each query then searched
  10 graphs, and QPS was 210 / 224 / 351 (1 / 8 / 32 clients). `docker/milvus-user.yaml` raises the
  seal size, which gives 2 segments and 352 / 777 / 589 QPS. The table shows the tuned run.
- **Milvus** searches with `consistency_level="Eventually"`, because the data is read-only after the build.
- **FAISS** is a library, not a DB. It has no persistence, CRUD, BM25 or server hop, so treat its numbers
  as the lower bound for latency.
- **Warm-up:** the 2026-10-20 run warmed up with only 100 queries. The lowest-ef points of Milvus
  and OpenSearch were therefore slower than the next ef (visible in the chart). The comparison at
  recall ≥ 0.95 is not affected. `bench.py` now warms up with every query at ef=512.
- **Synthetic qrels** mark exactly one relevant chunk per query. Other chunks that also answer the
  question count as misses, so absolute scores are pessimistic. Compare relative differences.

## Part 2: agentic RAG

Eight tracks on the same corpus, retriever (OpenSearch on the PGX: nori BM25, bge-m3, bge-reranker-v2-m3) and
answer model (OpenRouter `qwen/qwen3.8-27b`, DeepInfra pinned, thinking off). Only the decision-maker or the
architecture changes. The eval set has 300 main questions over six intents (doc_qa, multi_doc, doc_calc,
out_of_corpus, chitchat, calc), 30 ACL questions, 80 distractor-tool questions and a 20 × 3 consistency set.
The Hermes tracks run a stratified 120-question subset to keep the cost near $2; the whole run cost about $3.3.

| Track | What decides | 120-q accuracy | Refuses unanswerable | Input tokens/q | p50 |
| --- | --- | --- | --- | --- | --- |
| B0 | nothing: always hybrid+rerank → answer | 0.575 | 1.00 | 1.6k | 2.2 s |
| W-llm | RAG workflow, Qwen decides intent / mode / sufficiency | 0.800 | 1.00 | 2.5k | 4.7 s |
| W-kev / W-laya | same workflow, Kev-4B / Laya decide | 0.642 / 0.375 | 1.00 / 0.48 | 0.8k / 1.0k | 3.1 / 1.1 s |
| A1 | Hermes Agent with search tools over MCP | **0.850** | 0.72 | 24.9k | 17.5 s |
| A2 | Hermes Agent with one RAG-layer tool (W-llm inside) | 0.775 | 0.92 | 18.4k | 15.9 s |

- **The agent wins multi-step questions but is ungrounded and costly.** A1 scored 0.80 on multi_doc (W-llm 0.60)
  and 0.53 on doc_calc (W-llm 0.40). It also answered 28% of questions it should have refused, used 10× the
  tokens and had a p95 near 2 minutes.
- **A2's quality is its RAG layer's quality.** The LLM mode router picked bm25 96% of the time and the
  sufficiency gate refused 22% of answerable questions. A2 inherited both.
  Recommendation: an agent runtime plus a RAG layer that always runs hybrid+rerank and gates on reranker scores
  ([recommendations](wiki/decisions/2026-10-23-recommendations.md)).
- **Kev-4B routes like the LLM; Laya does not.** Intent macro-F1 is 0.79 for Kev, 0.74 for Qwen and 0.21 for
  Laya. Tool choice is about 0.82 for Kev from 4 to 20 tools, 0.79–0.84 for Qwen native tool calling and
  0.50 → 0.26 for Laya. Kev's yes/no sufficiency is badly calibrated (52% false refusals), so W-kev ends at
  0.66 end to end against 0.78 for W-llm. Verdict: Laya NO-GO; Kev conditional GO as a first-stage router
  with LLM fallback, not as a gate.
- **Qwen picking a label as JSON beat native tool calling** for tool selection (0.93–0.96 against 0.79–0.84)
  and was 3–4× faster.

Run it (see [AGENTS.md](AGENTS.md) for the rules and `scripts/serve-agentic.sh` for the PGX side):

```bash
uv sync --extra agentic
ssh pgx bash serve-agentic.sh && scripts/tunnel.sh   # Qwen/embed/rerank/OpenSearch/Kev/Laya; loopback + ssh tunnel
export PGX_HOST=<model host> LLM_URL=https://openrouter.ai/api/v1/chat/completions \
       LLM_MODEL=qwen/qwen3.8-27b LLM_KEY=<key> OR_PROVIDER=deepinfra
uv run --extra agentic python -m rag_bench.agentic.evalset           # data/agentic_eval.parquet
WORKERS=4 scripts/run-agentic.sh w-llm 8111                          # one track: run + judge (main acl consistency)
SMALL=1 WORKERS=3 scripts/run-agentic.sh a1 8121                     # Hermes tracks on the 120-q subset, one at a time
uv run --extra agentic python -m rag_bench.agentic.toolsel kev       # tool-selection sweep (4/10/20 tools)
uv run --extra agentic python -m rag_bench.agentic.report            # results/agentic/REPORT.md
```

Hermes Agent is installed outside the repo (NousResearch/hermes-agent at `bf0203a`, Python 3.14, `[mcp]`).
Gotchas are in [the Hermes lesson](wiki/lessons/2026-10-23-hermes-and-qwen-serving.md).
