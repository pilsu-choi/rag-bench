# Results of the 2026-10-20 run

All tables are in [results/REPORT.md](../../results/REPORT.md), and the chart is
[ann_pareto.png](../../results/ann_pareto.png). The numbers below are for the `full` scale
(209,069 vectors) unless noted.

## What it means

1. **The store hardly changes search quality.** All four give the same dense results, so ANN loss is
   negligible at ef 256. Korean BM25 is similar across analyzers, with nori slightly ahead. Hybrid
   search adds about 0.04 nDCG@10 and reranking about 0.09–0.12.
2. **End-to-end latency is dominated by the models.** Embedding plus reranking (~256 ms) dwarfs a
   2–7 ms search. Reranker depth and size are the main latency knobs.
3. **The stores differ on filters, throughput under concurrency, and memory.**
   - Milvus keeps filtered recall high at every selectivity.
   - pgvector uses the planner, which gives exact results for very selective filters, but it slows
     down once the table outgrows memory.
   - OpenSearch has the best concurrent throughput and BM25, but it uses the most memory and takes
     the longest to build.
   - FAISS is the latency floor, but it has no DB features.
4. **A rough guide for about 1,000 documents:**
   - pgvector if Postgres is already in the stack.
   - Milvus if metadata filtering and growth matter.
   - OpenSearch if Korean keyword search and hybrid search matter.

Caveats are in [issues](../issues/index.md). The most important are OpenSearch's untuned
filtered-search threshold and the single-relevant-chunk qrels.
